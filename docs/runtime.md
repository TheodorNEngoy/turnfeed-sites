# Runtime and operational limits

Public Sites website with a personal native plugin candidate. It retains Turnfeed's 24-tool chat core and adds private settings, account privacy, follow-request controls and a private account export tool, with ChatGPT identity and Sites-managed hosting and D1 persistence.

The retained source is from `TheodorNEngoy/chatgpt-social-mvp` commit `1e1aa821f983f4e8234a16f68fe15915dc5aef26`. `vendor/turnfeed/server.js` is never imported or started. A deterministic extraction keeps the registered handlers and their validation, approval, ownership, moderation, and receipt logic. Platform boundaries are explicit adapters in `worker/`.

This is a separate candidate with fresh data. The website complements the native in-chat experience, with ChatGPT sign-in, Sites hosting and storage. Legacy Auth0 accounts and historical data are outside the migration scope. Choose further features by their benefit to native Turnfeed users. Public distribution, native approval behavior and production scale require verification before a wider launch.

## Runtime

Sites is the only authentication boundary. Tool inputs cannot supply identity. Every request receives its own core instance and loads durable data from D1. All successful mutations and confirmation state must be committed atomically before a success response leaves the Worker.

Successful post creation returns the exact saved post ID, its readable content and reply target. Identical retries retain the original reference, even after newer posts exist. Ordinary new posts need no preliminary lookup before an explicitly approved reply. Retries with existing replies and quote posts require a thread read using the supplied ID; hidden posts return no readable reference, and archived posts offer no reply handoff. These fields add no storage query and never authorize a reply by themselves.

ChatGPT’s optional sign-in account name initializes an unnamed profile. It may differ from the separate public ChatGPT profile name; this is an initial import, not profile synchronization. A chosen name or handle is preserved, and explicit name changes, clears and account resets prevent automatic reinitialization. Names use the existing profile validation; email is never a public-name fallback.

The public website accepts one JPEG/PNG through Add photo in the post composer, including when used in Codex’s sidebar. The form supports a local preview and removal before an explicit Post; no plugin installation is required. The bounded multipart route checks Site identity, origin and its signed account-bound form token before storage. Selected chat photos also use the documented `openai/fileParams` contract on `create_post.photo` (JPEG/PNG only). The server fetches only bounded HTTPS OpenAI attachment URLs, strips embedded metadata, and stores bytes privately in Sites R2; no temporary download URL or original filename is persisted. D1 keeps small owner-bound metadata and atomic quotas: 1 MiB/file, 4096 pixels per side, 16 megapixels, 20 MiB/account, 100 MiB/global, 10 new uploads/account/UTC day and 1024 object rows including tombstones. Photos render in the feed, thread and quote views. Every image fetch rechecks post visibility; operator-only review covers hidden photos and retained report evidence. Post deletion/reset removes ordinary photos; erasure also clears unlinked ready photos. Ambiguous uploads remain private and charged for reconciliation. Publication and definite-rejection retirement share a D1 transaction guard so concurrent calls cannot attach deleted files. JPEG/PNG structure validation is not content classification or full pixel decoding. The personal plugin’s host file transfer still needs an attached-file live check; this does not gate the website uploader. Video-file uploads, arbitrary remote media fetching and Events delivery remain disabled. The website makes HTTP(S) links clickable and recognizes public YouTube/Vimeo video links in post and reply text. Each message displays at most one video card; shortened reply previews and quotes contain links only. Players load only after an explicit browser click, use fixed provider origins, do not autoplay and can be closed. Opening another player closes the previous one. No thumbnails or metadata are fetched. Native tool content and publication, moderation and deletion behavior are unchanged; provider availability and embedding permissions still apply.

`get_my_settings`, `update_my_settings` and `mute_user` bring the existing private preferences into chat: hidden words, notification filters and mute/unmute. Changes preserve unspecified settings, concurrent updates merge, and muted lists use bounded pages with viewer-bound cursors. Mute keeps following and profile access intact. The website now shares this native feed and account identity. It supports chronological and active feeds, paginated conversations, posts, replies to posts and replies, profile edits and confirmed deletion of your own post and its reply tree. Nested-reply forms show the selected message and bind its exact native handoff to the account and retry token. Browser forms call the same native handlers without a model call. They require Sites identity, same-origin submission and signed, account/action/target-bound tokens with a 30-minute expiry; posts and replies retain a stable client ID for retries. Public Site access and plugin distribution remain separate decisions. See [the port comparison](native-parity.md) for retained behavior and remaining gaps.

D1 stores profiles, posts (including reply trees), relationships, controls, receipts and moderation records separately. Stable record IDs and a manifest preserve exact ordering; large records are chunked. Small edits write only changed records. A global revision compare-and-swap and a single D1 batch commit content, receipts, admission rules and audit records together. Confirmed stale requests have no storage effects.

Complete state reads use one SELECT for an initialized database. Head initialization runs only after an empty result, followed by a fresh SELECT so a concurrent first writer is preserved. The empty-database path reserves all three operations before it initializes; failed reads never trigger initialization. This removes one sequential database operation from ordinary feed and write requests without changing the stored format. Hosted latency savings have not been measured.

For format-2 states up to 64 KiB, feed, thread and private-settings reads fetch and validate all record payloads in the initial SELECT. Later projections use only that request's cache, reducing an ordinary small thread read from three queries to one. The size decision, head and payloads share one database snapshot; full digest and byte-count checks still apply. Larger states retain selective payload queries. This changes no schema or stored data. Fewer round trips are verified locally; total hosted latency remains variable.

`get_my_settings` uses a selective read for larger format-2 data: it loads the manifest and digest index, the caller's preferences/admission/name records, and profiles for only the requested muted page. Each payload query is bound to the original revision; a concurrent change restarts the read. The manifest and selected values are hash-checked. Unread payload bytes are checked when a complete read next loads them. A projection never enters the commit path. Legacy data and requests that may import an initial ChatGPT name use the complete path to preserve migration and name behavior.

In a local 2,130,568-byte fixture with 2,400 unrelated profiles and retained evidence, a one-member settings page reduced serialized query-result bytes from 3,257,939 to 679,789 (**79.1%**), using three SELECTs instead of a head-initialization statement plus one complete SELECT. This measures local data transfer, not hosted latency or throughput. The digest index still grows with total record count.

Ordinary non-quoted `get_thread_context` reads also use a projection: the complete selected post/reply tree, participant profiles, actor preferences and both directions of participant blocks. It reuses the retained visibility, correction-history, ordering, pagination and rendering helpers while skipping feed-ranking work unused by thread output. Quoted/group/non-public targets, missing or ambiguous stable IDs, legacy storage and possible initial-name imports retain the complete path. A concurrent revision change restarts the whole projection; it cannot commit partial state.

In a local 2,308,719-byte fixture containing 500 unrelated posts/profiles and retained evidence, a thread read reduced serialized query-result bytes from 3,019,459 to 418,456 (**86.1%**) with three SELECTs. Complete tool output matched the retained full reader. This is a local transfer measurement; hosted latency remains unmeasured. The entire selected reply tree is still loaded even for one page.

`get_feed_digest`, including the website's Active and Latest feeds, uses a read-only projection. Larger states load the manifest/digest index and then the complete conversation, profile and relationship inputs required by the retained ranker, plus the caller's preferences and closure/name state. Posting receipts, reports, moderation history, delivery records and unrelated private preferences remain in D1. Both reads are bound to one revision; conflicts restart the projection. Ranking, visibility and pagination use the same core handler. First-name imports, legacy migration and requests that also need activity events retain the full path. The projected state can never enter `commitState`.

In a local 1,219,544-byte fixture with 100 conversations, 10,000 receipt digests and 80 retained report snapshots, the feed projection reduced serialized query-result bytes from 1,354,720 to 270,353 (**80.0%**) using two SELECTs. Small initialized feeds retain one SELECT. Exact output comparisons cover all four focuses, viewers, pagination, filtering and quotes. This is a transfer measurement for that fixture, not a measured improvement in hosted response time; stores dominated by conversation data will save less.

Writes and other actions still load the full snapshot; feed reads still load all conversation trees and relationship history needed for ranking. A **4 MiB serialized-state ceiling**, including the record manifest, and **8,192 row ceiling** remain; at most two requests run per isolate. Selective loading reduces avoidable transfer and hydration but does not remove these limits. Before substantial growth, add an indexed, bounded feed representation and measure hosted memory/throughput. An individual large reply tree or owner receipt ledger may span multiple rows and is still rewritten as one logical record.

Migration 0001 only adds schema. The first successful MCP call with existing legacy data converts the old representation atomically, preserving data and removing obsolete legacy chunks in the same transaction. A failed conversion leaves the old data intact. Updates and erasure remove obsolete record parts so ordinary deleted data is not left in a second copy. **After conversion, the old Worker cannot read the new format**: a code rollback must retain the format-2 storage adapter; do not deploy the pre-migration Worker against converted data. Applied SQL migrations and their metadata remain immutable.

Confirmed CAS misses may retry the entire tool wrapper within a 45-statement request budget. An ambiguous database response never retries automatically; the user must inspect current state first. Existing public-write client IDs remain durable and suppress duplicate post/reply retries.

## Private account controls in chat

`export_my_data` returns the signed-in user's profile/settings, relationships, own posts with readable conversation context, own replies in readable threads and report receipts. Exports exclude internal safety and operational records and complete notification/like history. Each page contains at most 8,192 UTF-16 characters of JSON, preserves Unicode pairs, and uses a signed continuation bound to the account, data revision, document digest and ten-minute expiry. Concatenate pages in order and verify the SHA-256 before calling the export complete. The export has no public download URL. A changed revision requires restarting instead of combining different versions. Feed-only activity labels are omitted so clock changes cannot alter the same export's content.

In-chat account closure is temporarily disabled. The earlier model-visible token and phrase did not prove confirmation from a later human message. Both `preview_my_account_closure` and `close_my_account` are absent from discovery; cached calls fail before reading storage or processing arguments. No closure plan is issued. Re-enabling closure requires a trusted human-action confirmation mechanism and verification of that boundary, not a delay or model-supplied turn identifier.

For account closure, contact the operator of your deployment. The separately authorized operator erasure workflow remains available. `reset_me` clears ordinary data and re-enrolls the account; it does not close access and must not substitute for closure. Exports remain private and read-only.

## Operator tools

`/operator` provides reports, original report captures, retained moderation evidence, hide/restore actions, account erasure and audit history. An authenticated ChatGPT user has no operator rights unless their derived 40-character account key is explicitly listed in the secret `TURNFEED_OPERATOR_ACCOUNT_KEYS` environment variable. Comma-separated keys are supported.

To configure the first operator while the Site is owner-private, temporarily deploy with `TURNFEED_OPERATOR_SETUP=1`. An installed native tool call to the verified own profile returns `structuredContent.turnfeedSitesAccountKey`. Use that exact key in `TURNFEED_OPERATOR_ACCOUNT_KEYS`, remove the setup variable and redeploy the saved version. Do not guess or derive it from a workspace account ID. Never enable setup on a shared Site.

Every operator write requires a signed preview bound to the operator, action and current database revision. Account erasure also requires the exact account-and-case confirmation. The ordinary data removal, retry-record cleanup, durable access closure and erasure receipt commit together. Closed accounts cannot recreate their data through existing connections or retain operator access. This is Turnfeed-level closure; OpenAI-issued tokens and the ChatGPT account remain unchanged. Moderation evidence, other users' safety blocks and minimal audit records remain available for their stated purpose.

The private candidate has a bounded 500-account erasure journal. A capacity or ambiguous database error never silently drops evidence or retries an operator write.

## Automatic public-content screening

Durable D1 counters limit actual moderation API requests to 30 per account and 300 across the Site per minute, including rejected content and failed API calls. Expired counters are removed and the table is capped at 4096 rows. This requires migration `0003_moderation_limits.sql`; unavailable counter storage stops new screening requests. Already-published identical retries still return their saved receipt without another API call.

Set `OPENAI_API_KEY` as a secret in Sites (never in the bundle). The server calls only OpenAI’s free `omni-moderation-latest` endpoint. New or changed post/reply text, profile fields and photo uploads from both public and private accounts must pass before publication. Rules, spam limits, reports and operator review remain in place. Missing credentials, rate limits, malformed responses and timeouts stop publication; they do not silently bypass screening. Approved results are reused only within the same request for identical content during a definite database retry. Private settings, report evidence and private chat content are not sent. Photos are screened after format validation/metadata stripping and before file storage; existing staged files are checked when reused.

This is automated content screening, not a guarantee of safety or a dedicated CSAM detection system. Do not send known or suspected CSAM to the API. Handle child-safety reports through restricted operator review and the applicable reporting process. Do not use real abusive imagery as test fixtures. Native video uploads are not part of this release.

## Profile pictures

My profile supports an explicit JPEG/PNG upload, local preview, replacement and removal. These use the existing screening, size, account/day and Site storage caps. A separate signed browser form binds the actor and expected current picture; raw MCP avatar URLs remain rejected. Public feed, thread, reply and quote projections include the current author picture. Image reads enforce ownership, account revocation and both block directions. Replacement/reset removes unreferenced ordinary objects; operator removal retains restricted evidence through the existing signed review/commit flow. Profile pictures are not imported automatically from ChatGPT.

## Website social controls and photo preparation (2026-10-08)

The website exposes the retained follow/unfollow and post/reply like/unlike handlers through signed forms. Author names and pictures open public profiles. My profile links to a paginated Following list. Desired-state actions, fresh target checks and existing block/revocation rules remain enforced. Private accounts use the approved-follower controls below.

With JavaScript, the browser accepts JPEG/PNG originals up to 8 MiB and 32 megapixels, prepares post images at up to 2048 pixels on the longest side and avatars at up to 512 pixels, and previews the exact prepared file before submission. It preserves aspect ratio and PNG transparency, never enlarges images, and blocks submission while preparing or after a preparation failure. Stored uploads still must meet the existing 1 MiB and server dimension limits; browser preparation is not trusted server validation. Without JavaScript, original files must already satisfy the server limits.

## Private accounts and approved followers (2026-10-08)

My profile → Privacy and followers exposes public/private account choice, pending-request approval or decline, and follower removal. Accounts stay public by default. Switching to private protects existing and new posts, replies, photos, bio and avatar; names and handles remain discoverable. Existing followers keep access and can be removed. New follows become requests and give no access until accepted. Going public clears pending requests without approving them. Private replies also require access to their root and every ancestor. New quotes of private-source posts are refused; existing quote previews recheck source access. Content people already copied cannot be recalled, and restricted moderation evidence remains available to operators.

The retained `follows` map contains only approved edges. Pending requests with unique IDs and `privateAccount` live in normalized profiles; no database schema change is needed. Profile edits preserve privacy. Follow acceptance binds the signed-in owner, viewer-bound person reference, readable name and exact pending request ID. Blocks and reset clear related requests. Browser forms bind the actor/action and observed privacy setting; stale approvals cannot accept a cancelled/recreated request.

`get_my_privacy`, `set_account_privacy` and `manage_follower` provide the same controls to the native candidate. Lists use bounded pages and account/state-bound cursors. The retained tool parameter `visibility: "public"` is a compatibility acknowledgement; it never overrides account privacy. Both complete and selective readers enforce private-author access. Direct avatar/photo URLs enforce current access and use no-store responses. Ordinary export context/report receipts are redacted when current target access cannot be established; operator evidence stays separately authorized.

Privacy changes are covered by isolated multi-account tests. Hosted identity provenance and hosted D1 atomicity remain platform assumptions; local checks do not independently certify those boundaries. Never roll back to a build without account-privacy enforcement once any account has opted into private mode.
